# 조건부 UPDATE 실제 신청 경로 적용 결과

- 실행일: 2026-08-20
- 개선 전 커밋: `1132876`
- DB: Docker MySQL 8.0
- Java: 17
- 대상: `PlannerService.applyCourse()`

## 문제

개선 전 실제 신청 경로는 다음 순서로 동작했다.

```text
강의 조회
-> 현재 카운터로 정원 확인
-> 신청 내역 저장
-> 실제 신청 행 수를 COUNT
-> applied_count 덮어쓰기
```

정원 확인과 저장이 하나의 원자적 연산이 아니므로, 정원 10명에 100개 동시 요청을 보낸 결과 13건이 저장됐고 `applied_count` 12와도 불일치했다.

## 변경

`CourseRepository` 에 다음 조건부 갱신을 추가했다.

```sql
UPDATE courses
SET applied_count = applied_count + 1
WHERE id = ?
  AND applied_count < limit_count
  AND canceled = false;
```

`PlannerService.applyCourse()`의 흐름을 다음과 같이 변경했다.

```text
강의·폐강·중복·학점·시간표 검증
-> 조건부 UPDATE
-> 변경 행 0개: 마감 거절
-> 변경 행 1개: 신청 내역 INSERT
-> 둘 다 성공하면 COMMIT
-> 후속 저장이 실패하면 모두 ROLLBACK
```

JPQL 벌크 UPDATE는 영속성 컨텍스트의 기존 `Course` 객체를 자동으로 갱신하지 않는다. 그러므로 `clearAutomatically = true`로 UPDATE 후 캐시를 비워 후속 조회가 DB의 최신 카운터를 읽게 했다.

공통 조건:

- 서로 다른 사용자 100명
- 동시 요청 100개
- 스레드 풀 32개
- 같은 MySQL 8.0 테스트 인스턴스

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 개선 전 | 13 | 27 | 60 | 13 | 12 | 3건 |
| 조건부 UPDATE 후 | 10 | 90 | 0 | 10 | 10 | 0건 |

## 중복 신청 검증

같은 학번이 같은 강의에 두 번 동시 신청하는 상황을 재현했다.

```text
success=1
duplicate_rejected=1
unexpected_failure=0
actual_applications=1
applied_count=1
```

코드의 사전 중복 조회는 빠른 거절을 담당하고, DB의 `(student_id, course_id)` UNIQUE 제약은 두 요청이 사전 조회를 동시에 통과한 경우의 최종 방어선이다. UNIQUE 충돌은 `IllegalStateException("이미 신청된 과목입니다.")`로 변환했다.

## Rollback 검증

같은 트랜잭션 안에서 조건부 UPDATE와 신청 INSERT를 실행한 후 의도적으로 예외를 발생시켰다.

```text
applied_count=0
actual_applications=0
```

정원 증가와 신청 내역이 함께 원복되어, 두 상태 변경이 하나의 원자적 작업으로 처리되는 것을 확인했다.

## 선택 근거

조건부 UPDATE를 실제 신청 경로에 선택한 이유는 다음과 같다.

1. DB가 정원 확인과 증가를 SQL 하나로 처리한다.
2. 락 충돌 예외를 재시도하는 대신 UPDATE 결과 0개를 명확한 마감 결과로 변환할 수 있다.
3. 신청 INSERT와 같은 트랜잭션에 두어 후속 실패 시 카운터도 롤백한다.
4. 비관적 락처럼 조회 시점부터 명시적 락을 유지하지 않고, 낙관적 락처럼 버전 충돌 재시도 정책을 요구하지 않는다.

이 선택을 정합성뿐 아니라 실행 비용 측면에서도 확인하기 위해 2026-09-03에 동일한 좌석 선점 핵심을 전략별 3회 반복했다.

| 전략 | 전체 소요 중앙값 | p95 중앙값 | 처리량 중앙값 | 충돌·재시도 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| 비관적 락 | 79.83ms | 72.58ms | 1252.58 req/s | 0회 |
| 낙관적 락 | 196.75ms | 185.97ms | 508.25 req/s | 309회 |
| 조건부 UPDATE | 63.06ms | 57.65ms | 1585.90 req/s | 0회 |

세 방식 모두 성공 10건·마감 거절 90건으로 정합성을 지켰다. 고충돌 조건에서 낙관적 락은 반복 재시도 비용이 컸고, 현재의 단순 정원 규칙에서는 별도 선행 락 조회와 재시도가 없는 조건부 UPDATE가 가장 작은 비용을 보였다. 상세 결과는 `docs/concurrency/04-strategy-comparison-result.md`에 기록했다.

## 제한과 다음 작업

- 개선 전·후 Race Condition 수치는 로컬 MySQL의 1회 실험 결과이므로 성능 향상률로 사용하지 않는다.
- 전략 비교 수치는 같은 조건의 3회 중앙값이지만, 로컬에서 좌석 선점 핵심만 격리한 결과이므로 운영 HTTP 성능으로 일반화하지 않는다.
- 개선 전은 deadlock 60건, 개선 후는 정상적 마감 거절 90건으로 결과 종류가 다르므로 185ms와 174ms를 단순 성능 비교로 사용하지 않는다.
- 신청과 취소가 같은 강의에 동시에 수행되는 상황은 별도 검증이 필요하다.
- Render의 CPU·DB·HikariCP 병목은 이 정합성 실험과 분리해 A/B/C/D 부하 테스트로 확인한다.

## 테스트 검증 범위

MySQL 8.0에서 다음 테스트를 함께 실행해 통과했다.

- 기존 신청 검증: 학점 제한, 시간표 중복, 폐강, 마감, 중복 신청
- 정원 10명에 서로 다른 사용자 100명의 동시 신청
- 동일 사용자의 동시 중복 신청 2건
- 정원 증가와 신청 저장 후 강제 예외를 발생시킨 Rollback

전체 기본 테스트는 13개 중 9개 통과, MySQL 전용 3개 제외, 기존 로그인 라우팅 테스트 1개 실패였다. 실패한 테스트는 현재 비밀번호 `1234` 대신 과거 비밀번호 `dku1234!`을 사용하며 실제 시각 기반 로그인 허용 구간에도 의존한다. 이번 신청 로직 변경과는 무관하지만, 별도로 시계를 주입할 수 있게 바꾸고 테스트 값을 현재 설정과 맞추는 작업이 필요하다.

## 포트폴리오 요약

> 정원 10명의 강의에 100개의 동시 신청을 보내 기존 조회 후 저장 방식에서 13건이 등록되고 신청 카운터와 실제 행 수가 어긋나는 Race Condition을 재현했습니다. 정원 확인과 증가를 조건부 UPDATE 하나로 묶어 실제 신청 경로에 적용한 후, 동일 조건에서 성공 10건·마감 거절 90건·정원 초과 0건을 확인했습니다. 또한 동시 중복 신청은 1건만 저장되고, 후속 예외 시 카운터와 신청 내역이 함께 Rollback되는 것을 검증했습니다.
