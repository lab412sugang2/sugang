# 동시성 제어 전략 반복 비교 계획

- 작성일: 2026-09-03
- 상태: 결과 확인 전 가설
- 목적: 비관적 락, 낙관적 락, 조건부 UPDATE의 정합성과 비용을 동일 조건에서 비교한다.

## 문제

기존 한 번의 실행에서는 세 방식 모두 정원 10명을 지켰다. 그러나 단일 실행 시간만으로 특정 전략이 더 빠르다고 일반화할 수 없고, 낙관적 락의 충돌 비용도 충분히 기록하지 않았다.

## 비교 범위

이번 실험은 전체 수강신청 API가 아니라 **좌석 카운터 변경과 신청 행 저장**이라는 동시성 제어 핵심만 분리한다. 학점·시간표 검증이나 HTTP·Thymeleaf 비용을 제외해 전략 차이에 집중한다.

운영 테이블과 데이터를 변경하지 않도록 테스트 전용 InnoDB 테이블을 생성하고 테스트 종료 시 삭제한다.

## 동일 조건

| 항목 | 값 |
| --- | --- |
| DB | 로컬 Docker MySQL 8.0 |
| 격리 수준 | MySQL 기본값을 실행 결과에 기록 |
| 강의 정원 | 10명 |
| 요청 | 서로 다른 사용자 100개 |
| 동시 시작 | 100개 thread + `CountDownLatch` |
| Hikari max | 32 |
| 반복 | 전략별 3회 |
| 낙관적 충돌 처리 | version CAS 충돌 시 최대 100회 재시도 |

실행 순서는 다음과 같이 회전한다.

1. 비관적 → 낙관적 → 조건부 UPDATE
2. 낙관적 → 조건부 UPDATE → 비관적
3. 조건부 UPDATE → 비관적 → 낙관적

## 전략 구현

### 비관적 락

```sql
SELECT applied_count, limit_count
FROM concurrency_strategy_courses
WHERE id = ?
FOR UPDATE;
```

row lock을 획득한 뒤 정원을 검사하고 카운터 증가와 신청 행 INSERT를 같은 트랜잭션에서 수행한다.

### 낙관적 락

```sql
UPDATE concurrency_strategy_courses
SET applied_count = applied_count + 1,
    version = version + 1
WHERE id = ?
  AND version = ?
  AND applied_count < limit_count;
```

먼저 읽은 version과 일치할 때만 갱신한다. 변경 행이 0이면 충돌로 판단해 새 트랜잭션에서 다시 읽고 재시도한다.

### 조건부 UPDATE

```sql
UPDATE concurrency_strategy_courses
SET applied_count = applied_count + 1
WHERE id = ?
  AND applied_count < limit_count;
```

정원 검사와 카운터 증가를 한 SQL로 수행하고 변경 행 0/1로 마감과 성공을 판단한다.

## 결과를 보기 전 가설

1. 세 방식 모두 성공 10건, 마감 거절 90건, 정원 초과 0건을 유지할 것이다.
2. 비관적 락은 결과가 예측 가능하지만 모든 요청이 row lock을 순서대로 획득하므로 대기 비용이 생길 것이다.
3. 낙관적 락은 인기 강의처럼 충돌률이 높은 상황에서 재시도 횟수와 DB 왕복이 증가할 것이다.
4. 조건부 UPDATE는 별도 선행 조회와 애플리케이션 재시도가 없어 현재의 단순 정원 규칙에서 가장 작은 비용을 보일 것으로 예상한다.

## 수집 항목

- 성공, 마감 거절, 재시도 소진, 기타 실패
- 낙관적 충돌·재시도 횟수
- 100개 요청 전체 완료시간과 처리량
- 모든 최종 응답의 p50, p95, p99
- 실제 성공 요청의 p95
- 최종 카운터와 실제 신청 행 수
- 정원 초과와 카운트 불일치

전체 요청 p95·p99에는 성공과 마감 거절을 모두 포함한다. 이는 사용자가 최종 결과를 받을 때까지의 시간이다. 성공 p95는 좌석을 실제 획득한 10건만 별도로 본다.

## 판단 원칙

- 정합성을 지키지 못한 전략은 속도와 관계없이 제외한다.
- 3회 중앙값과 실행별 범위를 함께 본다.
- 낙관적 락은 최종 응답시간뿐 아니라 충돌·재시도 비용도 판단한다.
- 이 결과는 좌석 배정 핵심의 비교이며 전체 API 성능으로 일반화하지 않는다.
- 로컬 MySQL 결과를 Render-Railway 운영 성능 수치와 섞지 않는다.
