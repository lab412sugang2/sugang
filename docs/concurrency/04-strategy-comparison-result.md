# 동시성 제어 전략 반복 비교 결과

- 실행일: 2026-09-03
- 목적: 비관적 락, 낙관적 락, 조건부 UPDATE의 정합성과 실행 비용을 동일 조건에서 비교한다.
- 환경: 로컬 Docker MySQL 8.0.45, `REPEATABLE-READ`
- Java: 소스 호환성 17, 테스트 런타임 OpenJDK 25.0.2
- 사전 계획: `docs/concurrency/03-strategy-comparison-plan.md`
- 원본 결과: `docs/concurrency/raw/strategy-comparison/20260903-121937/`

## 실험 조건

| 항목 | 값 |
| --- | --- |
| 강의 정원 | 10명 |
| 동시 요청 | 서로 다른 사용자 100명 |
| 애플리케이션 스레드 | 100개 |
| Hikari 최대 connection | 32개 |
| 반복 횟수 | 전략별 3회 |
| 실행 순서 | P→O→C / O→C→P / C→P→O |
| 낙관적 재시도 | version CAS 충돌 시 최대 100회 |

실행 순서에 따른 워밍업·캐시 편향을 줄이기 위해 순서를 회전했고, 측정 전에 각 전략을 한 번씩 워밍업했다. 세 전략은 실제 서비스 코드가 아니라 동일한 좌석 선점 규칙만 구현한 테스트 전용 InnoDB 테이블에서 비교했다.

## 구현 방식

### 비관적 락

```sql
SELECT applied_count, limit_count
FROM concurrency_strategy_courses
WHERE id = ?
FOR UPDATE;
```

트랜잭션이 row lock을 획득한 뒤 정원을 검사하고 카운터 증가와 신청 행 저장을 수행했다. 다른 요청은 앞선 트랜잭션이 끝날 때까지 기다린다.

### 낙관적 락

```sql
UPDATE concurrency_strategy_courses
SET applied_count = applied_count + 1,
    version = version + 1
WHERE id = ?
  AND version = ?
  AND applied_count < limit_count;
```

먼저 읽은 `version`이 유지된 경우에만 갱신했다. 변경 행이 0개이고 아직 마감되지 않았다면 충돌로 판단해 새 상태를 읽고 재시도했다.

### 조건부 UPDATE

```sql
UPDATE concurrency_strategy_courses
SET applied_count = applied_count + 1
WHERE id = ?
  AND applied_count < limit_count;
```

DB가 정원 검사와 증가를 한 문장에서 수행하게 했다. 변경 행 1개는 성공, 0개는 마감으로 처리했다.

## 정합성 결과

9번의 측정에서 모두 같은 결과가 나왔다.

| 전략 | 성공 | 마감 거절 | 재시도 소진 | 기타 실패 | 최종 카운터 | 신청 행 | 불일치 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 비관적 락 | 10 | 90 | 0 | 0 | 10 | 10 | 0 |
| 낙관적 락 | 10 | 90 | 0 | 0 | 10 | 10 | 0 |
| 조건부 UPDATE | 10 | 90 | 0 | 0 | 10 | 10 | 0 |

세 방식 모두 정원 불변식을 지켰다. 따라서 선택 기준은 단순히 정합성 보장 여부가 아니라 현재 충돌 패턴에서 필요한 DB 작업과 재시도 비용이다.

## 성능 결과

전략별 3회 중앙값이다. p95·p99는 성공 10건과 마감 거절 90건을 모두 포함한 최종 응답시간이다.

| 전략 | 전체 소요 | 처리량 | p95 | p99 | 성공 p95 | 충돌·재시도 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 비관적 락 | 79.83ms | 1252.58 req/s | 72.58ms | 74.16ms | 34.79ms | 0회 |
| 낙관적 락 | 196.75ms | 508.25 req/s | 185.97ms | 192.04ms | 156.20ms | 309회 |
| 조건부 UPDATE | 63.06ms | 1585.90 req/s | 57.65ms | 58.72ms | 27.37ms | 0회 |

조건부 UPDATE의 전체 소요시간 중앙값은 비관적 락보다 약 21.0%, 낙관적 락보다 약 67.9% 짧았다. 처리량 중앙값은 비관적 락보다 약 26.6%, 낙관적 락보다 약 212.0% 높았다.

## 왜 이런 결과가 나왔는가

### 비관적 락

정합성은 명확했지만 모든 요청이 `SELECT ... FOR UPDATE`에서 같은 row lock을 순서대로 획득했다. 정원 확인을 위한 조회와 갱신이 분리되어 조건부 UPDATE보다 DB 작업이 하나 더 필요했다.

### 낙관적 락

인기 강의 하나에 100개 요청이 집중되므로 충돌이 드물다는 전제가 성립하지 않았다. 세 번의 실험에서 209회, 309회, 310회의 충돌·재시도가 발생했다. 재조회와 CAS UPDATE가 반복되며 DB 왕복과 최종 응답시간이 가장 크게 증가했다.

### 조건부 UPDATE

정원 검사와 증가를 UPDATE 한 번으로 처리했고 애플리케이션 재시도가 없었다. 현재 규칙이 `applied_count < limit_count`라는 단순 조건으로 표현되기 때문에 세 방식 중 실행 경로가 가장 짧았다.

## 선택

현재 서비스의 좌석 선점에는 조건부 UPDATE를 유지한다.

1. 세 방식 모두 정합성을 지켰다.
2. 조건부 UPDATE는 현재 규칙을 SQL 한 문장으로 표현할 수 있다.
3. 이번 고충돌 조건에서 재시도 없이 가장 짧은 중앙 응답시간과 가장 높은 처리량을 기록했다.
4. 변경 행 수 0/1을 마감/성공이라는 도메인 결과로 바로 변환할 수 있다.

이 선택은 조건부 UPDATE가 항상 가장 빠르다는 의미가 아니다. 여러 엔티티와 복잡한 검증을 먼저 고정해야 한다면 비관적 락이 더 단순할 수 있고, 충돌이 드물며 읽기가 대부분인 상황에서는 낙관적 락이 유리할 수 있다.

## 한계

- 전략별 3회인 소규모 실험이므로 통계적 일반화에는 부족하다.
- 로컬 MySQL에서 좌석 선점 핵심만 격리한 결과이며 HTTP, Thymeleaf, Render 네트워크 비용은 포함하지 않았다.
- Hikari 최대 connection을 32개로 고정했기 때문에 다른 pool 크기에서 수치가 달라질 수 있다.
- 조건부 UPDATE도 동일 row 변경을 병렬화하지 않는다. 운영 C/D 실험에서 확인한 hot-row 직렬화 문제는 별도의 성능 병목이다.
- 실제 서비스 선택은 이 결과와 함께 중복 신청, 후속 실패 Rollback, 운영 부하 결과를 같이 판단해야 한다.

## 재현 방법

로컬 MySQL 컨테이너가 `3307` 포트에서 실행 중일 때 다음 명령을 사용한다.

```bash
DB_PASSWORD='<로컬 MySQL 비밀번호>' \
  ./scripts/concurrency/run_strategy_comparison.sh
```

실행 결과는 `tmp/concurrency-strategy-comparison/<실행시각>/`에 생성된다.
