# 성능 테스트 범위와 사전 가설

- 작성일: 2026-06-23
- 기준 태그: `v1.0-baseline`
- 기준 커밋: `ce8d7a0`
- 대상 URL: `https://sugang-5de3.onrender.com`
- 원칙: 정식 부하 테스트 전에 예상과 판단 기준을 먼저 기록한다.

## 목표

수강신청 연습 사이트가 실제로 어디서 먼저 한계에 도달하는지 찾는다.

목표는 Redis, Kafka, 캐시, 서버 증설을 먼저 넣는 것이 아니다. 현재 구조에서 어떤 지점이 먼저 포화되는지 측정하는 것이다.

## 테스트 상황

정합성 테스트는 다음 상황을 기준으로 한다.

- 강의 정원: 10명
- 사용자: 모두 서로 다른 사용자
- 대상 행동: 동일 강의 신청
- 동시 요청 수: 10, 50, 100, 300

성공 조건:

- 최종 등록 인원: 10명
- 정원 초과 등록: 0건
- 동일 사용자 중복 등록: 0건
- 5xx 오류 수 측정
- 평균 응답시간 측정
- p95 응답시간 측정
- p99 응답시간 측정
- 최대 처리량 측정

## 콜드 스타트 분리

Render Free 환경에서는 서버가 잠들 수 있다. 따라서 첫 접속 지연과 API 처리 성능을 섞으면 안 된다.

분리해서 측정한다.

- 콜드 스타트: 서버가 잠든 뒤 첫 요청까지 걸리는 시간
- 워밍업 상태: 서버가 이미 깨어난 뒤의 API 처리 성능

정식 병목 테스트는 별도 목적이 없다면 워밍업 상태에서 진행한다.

## 테스트 형태

### 지속 부하 테스트

일반적인 사용자가 반복해서 접속하는 상황에서 포화 지점을 찾는다.

- 1 VU
- 10 VUs
- 25 VUs
- 50 VUs
- 100 VUs
- 300 VUs

각 단계:

- Ramp: 30초
- Hold: 1~3분
- 최종 수치는 최소 3회 반복 후 판단

### 순간 동시신청 테스트

수강신청 특성에 맞게 같은 순간에 신청 요청이 몰리는 상황을 검증한다.

- 10개 동시 신청
- 50개 동시 신청
- 100개 동시 신청
- 300개 동시 신청

매번 대상 강의와 신청 데이터를 초기화한다.

## 테스트 3축

테스트는 크게 3개 축으로 나눈다.

| 테스트 | 목적 | 핵심 질문 |
| --- | --- | --- |
| 혼합 트래픽 | 가용성 확인 | 실제 사용 패턴에서 서버가 어디까지 버티는가 |
| 동일 강의 동시신청 | 정합성 확인 | 정원 10명에 100명이 몰려도 정확히 10명만 등록되는가 |
| 병목 분리 | 원인 분석 | 느려지는 지점이 앱, DB 조회, 쓰기, 락 경합 중 어디인가 |

## 병목 분리 세부 테스트

실제 신청 API 하나만 테스트하면 어디서 느려지는지 판단하기 어렵다.

따라서 병목 분리는 다음 4개로 쪼갠다.

| 구분 | 형태 | 확인하는 것 |
| --- | --- | --- |
| A | DB 없는 ping | Render, JVM, Tomcat, 기본 앱 처리 비용 |
| B | 단일 강의 DB 조회 | DB 연결, 조회 쿼리, 네트워크 지연 |
| C | 여러 강의 분산 신청 | 한 레코드에 몰리지 않는 쓰기 경로 |
| D | 동일 강의 집중 신청 | hot row 락 경합, 정원 정합성 |

해석 기준:

| 결과 | 유력한 원인 |
| --- | --- |
| A부터 느림 | Render CPU, JVM, Tomcat thread, 앱 자체 오버헤드 |
| A는 빠르고 B부터 느림 | DB 연결, 조회 쿼리, DB 네트워크 |
| B는 빠르고 C/D가 느림 | 쓰기 트랜잭션 경로 문제 |
| C는 빠르고 D만 느림 | 동일 강의 레코드 경합 또는 정원 갱신 방식 문제 |
| CPU는 낮고 Hikari pending 증가 | 커넥션이 쿼리, 락, 트랜잭션, 네트워크 때문에 오래 점유됨 |
| Heap과 GC 시간 증가 | 메모리 압박 또는 객체 생성 과다 |

## 수집할 지표

애플리케이션:

- `system.cpu.usage`
- `process.cpu.usage`
- `jvm.memory.used`
- `jvm.memory.max`
- `jvm.gc.pause`
- `tomcat.threads.busy`
- `tomcat.threads.config.max`
- `http.server.requests`

DB 커넥션 풀:

- `hikaricp.connections.active`
- `hikaricp.connections.idle`
- `hikaricp.connections.max`
- `hikaricp.connections.pending`
- `hikaricp.connections.acquire`
- `hikaricp.connections.timeout`

정합성:

- 실제 등록 인원
- 성공 요청 수
- 마감 거절 수
- 중복 신청 거절 수
- 5xx 수
- 최종 `courses.applied_count`
- 최종 `course_applications` 실제 행 수

## 1차 가설

Render Free는 CPU와 메모리가 제한적이므로, MySQL보다 애플리케이션 서버가 먼저 포화될 가능성이 높다고 예상한다.

예상 신호:

- 높은 VU에서 CPU가 90~100%에 근접한다.
- p95와 p99가 급격히 증가한다.
- VU를 올려도 처리량이 더 이상 증가하지 않는다.
- Hikari pending은 낮거나 0에 가깝다.

이 경우 1차 병목은 DB 커넥션 풀이 아니라 애플리케이션 런타임 또는 Render 인스턴스 자원일 가능성이 크다.

## 대안 가설

### Tomcat thread 포화

요청 처리 스레드가 오래 점유되어 대기열이 길어질 수 있다.

예상 신호:

- `tomcat.threads.busy`가 `tomcat.threads.config.max`에 근접한다.
- CPU가 100%가 아니어도 지연시간이 급증할 수 있다.
- 실패율은 낮은데 응답시간만 길어질 수 있다.

### JVM 메모리 또는 GC 압박

Heap 사용량이 늘고 GC가 자주 발생하면서 느려질 수 있다.

예상 신호:

- Heap 사용량이 max heap에 근접한다.
- `jvm.gc.pause` 횟수나 시간이 증가한다.
- p95보다 p99가 더 크게 튄다.

### DB 커넥션 풀 대기

DB 커넥션이 오래 점유되어 새 요청이 커넥션을 기다릴 수 있다.

예상 신호:

- `hikaricp.connections.active`가 `hikaricp.connections.max`에 계속 붙어 있다.
- `hikaricp.connections.pending`이 증가한다.
- `hikaricp.connections.timeout`이 증가한다.
- CPU가 반드시 높지는 않다.

주의:

이 신호가 나와도 바로 “커넥션 풀 크기를 늘리면 된다”고 결론 내리면 안 된다. 쿼리, 트랜잭션, 락 대기, DB 네트워크 지연 때문에 커넥션이 오래 잡혀 있을 수도 있다.

### DB 쿼리 또는 네트워크 지연

앱이 DB 왕복을 기다리느라 느려질 수 있다.

예상 신호:

- ping은 빠르다.
- DB 조회부터 느려진다.
- 부하가 커질수록 Hikari pending이 증가할 수 있다.
- 앱 CPU는 예상보다 낮다.

### 동일 강의 락 경합

같은 강의에 신청이 몰리면 하나의 강의 row를 둘러싼 경합이 생길 수 있다.

예상 신호:

- 여러 강의 분산 신청은 안정적이다.
- 동일 강의 신청만 느리거나 충돌이 많다.
- DB write latency 또는 lock wait이 증가한다.
- 기준 배포본의 `조회 -> 확인 -> 저장 -> 재계산` 방식에서는 정원 정합성 검증이 필요하다.

### 요청당 SQL 과다

신청 요청 한 번에 너무 많은 SQL이 실행되면 쓰기 경로가 느려질 수 있다.

예상 신호:

- DB 단순 조회는 안정적이다.
- 신청 API만 크게 느리다.
- 신청 1건당 SQL 수가 많다.
- 나중에 불필요한 조회를 줄이면 응답시간이 개선될 수 있다.

## 이미 수행한 로컬 동시성 실험

로컬 코드에는 다음 비교 실험이 존재한다.

- 테스트 파일: `src/test/java/sugang/service/ConcurrencyComparisonTest.java`
- 동시 요청 수: 100
- 정원: 10
- 비교 전략:
  - 비관적 락
  - 낙관적 락
  - 조건부 UPDATE

이 실험은 동일 강의 동시신청 정합성과 각 전략의 성능 차이를 보기 위한 것이다.

단, 이 실험은 로컬 코드 기준의 전략 비교이고, `v1.0-baseline` 배포본의 혼합 트래픽 병목 분석과는 분리해서 기록한다.

## 포화 지점 판단 기준

다음 변화가 처음 나타나는 지점을 포화 시작점으로 본다.

- 이전 단계 대비 p95가 급격히 증가한다.
- p99가 불안정해진다.
- VU를 올려도 처리량이 더 이상 증가하지 않는다.
- 5xx 또는 timeout이 발생한다.
- CPU가 90~100% 근처에 오래 머문다.
- `tomcat.threads.busy`가 최대치에 근접한다.
- `hikaricp.connections.pending`이 증가한다.
- `hikaricp.connections.timeout`이 증가한다.
- Heap이 Render 메모리 한계에 근접한다.
- 정원 초과 또는 중복 신청이 발생한다.

## 아직 하지 말 것

기준 측정 전에는 다음을 적용하지 않는다.

- Redis
- Kafka
- Render 플랜 업그레이드
- DB 커넥션 수 증가
- 쿼리 구조 변경
- 락 전략 변경
- 조건부 UPDATE를 운영 신청 로직에 바로 적용
- 캐시 추가

이들은 병목이 확인된 뒤 비교할 개선 후보일 뿐이다.
