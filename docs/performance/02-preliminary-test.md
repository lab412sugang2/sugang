# 예비 부하 테스트 결과

- 작성일: 2026-06-23
- 테스트 종류: 혼합 트래픽
- 대상 URL: `https://sugang-5de3.onrender.com`
- 목적: 본격적인 병목 분리 전에 대략적인 포화 지점을 찾는다.

## 테스트 목적

이 테스트는 정합성 테스트가 아니다.

목적은 실제 사용자 흐름에 가까운 요청을 섞어서 보냈을 때 Render Free 환경에서 어느 시점부터 응답시간이 급격히 나빠지는지 확인하는 것이다.

즉, 이 테스트가 답하는 질문은 다음이다.

```text
실제 사용 패턴에서 서버가 몇 명 부근부터 버거워지는가?
```

## 트래픽 구성

사용한 스크립트:

```text
k6/scenarios/fixed-stage-render.js
```

요청 비율:

- 홈 페이지 조회: 70%
- 시간표 팝업 조회: 15%
- 수강신청 요청: 15%

요청 흐름:

- 로그인 또는 부하 테스트 인증 우회
- 홈 조회
- 시간표 팝업 조회
- 신청 요청
- 각 VU가 루프를 돌며 반복

주의:

VU가 많다고 해서 모든 사용자가 정확히 같은 순간 같은 강의에 신청하는 것은 아니다. 따라서 이 테스트는 서버 가용성 테스트이지, 동일 강의 정합성 테스트는 아니다.

## 관찰 결과 요약

지금까지 확인한 핵심 사실:

- 100 VU는 안정적이었다.
- 300 VU도 안정적이었다.
- 500 VU부터 p95가 크게 증가했다.
- 500 VU와 1000 VU 구간에서 CPU가 100%에 도달했다.
- Hikari pending은 뚜렷한 병목 신호로 확인되지 않았다.

따라서 현재까지의 팩트는 다음이다.

```text
혼합 트래픽에서는 500 VU 부근부터 응답시간이 급격히 증가했고,
그 시점에 CPU가 100%에 도달했다.
```

## 해석 가능한 것

현재까지 말할 수 있는 것:

- 500 VU부터 혼합 트래픽 응답시간이 급격히 악화됐다.
- 같은 시점에 CPU가 100%에 도달했다.
- 따라서 병목 후보에서 CPU 또는 CPU를 많이 쓰게 만드는 처리 경로를 우선 의심할 수 있다.

## 아직 모르는 것

아직 결론 내리면 안 되는 것:

- Render 자체 CPU가 약해서 느린 것인지
- Thymeleaf 렌더링 때문에 CPU가 높은 것인지
- DB 조회가 많아서 CPU가 높아진 것인지
- 트랜잭션 처리 때문에 CPU가 높아진 것인지
- 동일 강의 락 경합 때문에 느린 것인지
- Hikari 병목이 아닌지 확정할 수 있는지

즉, 지금 결과만으로는 “CPU가 100%였다”까지만 말할 수 있다.

아직 “왜 CPU가 100%였는가”는 모른다.

## 병목 후보

가능성:

| 후보 | 설명 |
| --- | --- |
| A. Render 자체 CPU | Free 인스턴스의 CPU 한계로 요청 처리량이 제한됐을 수 있다. |
| B. DB 조회 | 홈 화면이나 신청 흐름에서 DB 조회가 많아 CPU와 지연시간이 증가했을 수 있다. |
| C. 트랜잭션 | 신청 처리 중 트랜잭션과 JPA flush 비용이 커졌을 수 있다. |
| D. 동일 강의 락 경합 | 같은 강의 신청이 섞이면서 row-level contention이 생겼을 수 있다. |
| E. Thymeleaf 렌더링 | 홈 화면 렌더링이 CPU를 많이 사용했을 수 있다. |
