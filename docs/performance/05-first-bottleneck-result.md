# Render-Railway 최초 병목 분석 결과

- 작성일: 2026-08-20
- 애플리케이션: Render
- 데이터베이스: Railway MySQL 9.4.0
- 격리 수준: `REPEATABLE-READ`
- HikariCP 최대 연결 수: 10
- 테스트 도구: k6, Micrometer, Prometheus, Grafana
- 개선 적용 여부: 없음

## 실험 목적

혼합 트래픽 실험에서는 500 VU부터 p95와 CPU가 함께 급증했다. 그러나 이 결과만으로는 Render CPU, DB 접근, 쓰기 트랜잭션, 동일 행 경합 중 무엇이 먼저 문제를 만들었는지 알 수 없었다.

따라서 이번 실험은 처리 경로를 다음처럼 분리했다.

| 구분 | 처리 경로 | 확인 대상 |
| --- | --- | --- |
| A | DB 없는 ping | Render, JVM, Tomcat, 기본 네트워크 |
| B | 강의 단건 조회 | DB 연결, 조회 쿼리, DB 네트워크 |
| C | 여러 강의 분산 신청 | 쓰기 및 트랜잭션 |
| D | 동일 강의 집중 신청 | 동일 행 경합과 정합성 |

## 공통 조건

- 워밍업된 Render 서버를 사용했다.
- 각 단계는 30초 동안 목표 VU까지 증가시킨 뒤 2분 30초 동안 유지했다.
- 서버 메트릭은 각 단계의 마지막 1분을 집계했다.
- 성공 응답의 p95와 p99를 계산하고 실패 요청은 별도 실패율로 기록했다.
- 대상 요청은 10초가 지나면 실패 처리하도록 변경했다.
- 임계치를 넘은 단계가 나오면 이후 고부하 단계를 자동 중단하도록 변경했다.
- 성능 개선, 커넥션 풀 증설, 캐시 추가는 하지 않았다.

## A. DB 없는 ping 결과

- Run ID: `20260820-214149`

| VU | 성공 p95 | 성공 p99 | 실패율 | 처리량 | Process CPU | Heap | Tomcat busy/max | Hikari pending |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 222.46ms | 258.70ms | 0% | 7.76 req/s | 13.00% | 45.14% | 1.00% | 0 |
| 50 | 217.45ms | 251.77ms | 0% | 39.16 req/s | 40.45% | 45.31% | 0.50% | 0 |
| 100 | 220.48ms | 258.82ms | 0% | 78.13 req/s | 13.88% | 42.13% | 0.50% | 0 |

### A 해석

VU를 10에서 100까지 높이는 동안 p95는 약 217~222ms로 유지됐고 처리량은 7.76 req/s에서 78.13 req/s까지 거의 선형으로 증가했다. 실패, Hikari 대기, Tomcat thread 포화, Heap 압박도 없었다.

따라서 100 VU 이하의 단순 요청에서는 Render CPU, JVM, Tomcat, 기본 네트워크가 최초 병목이라고 보기 어렵다.

50 VU에서 CPU가 일시적으로 40.45%까지 상승했지만 100 VU의 지연시간과 처리량이 안정적이었으므로 지속적인 CPU 포화 신호로 판단하지 않았다.

## B. 강의 단건 조회 결과

- 최초 실행 Run ID: `20260820-214149`
- 경계 탐색 Run ID: `20260820-221513`

| VU | 성공 p95 | 성공 p99 | 실패율 | 처리량 | Process CPU | Heap | Tomcat busy/max | Hikari active/max | Hikari pending |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 870.03ms | 927.89ms | 0% | 5.07 req/s | 9.13% | 47.24% | 4.50% | 80% | 0 |
| 20 | 848.63ms | 1070.91ms | 0% | 9.64 req/s | 11.20% | 57.17% | 6.00% | 100% | 1 |
| 30 | 793.39ms | 831.70ms | 0% | 15.83 req/s | 9.80% | 56.36% | 6.50% | 100% | 2 |
| 40 | 1273.15ms | 1311.35ms | 0% | 17.04 req/s | 7.60% | 56.38% | 10.50% | 100% | 10 |
| 50 참고값 | 1893.44ms | 측정 오류로 제외 | 1.61% | 3.25 req/s | 14.80% | 48.49% | 15.50% | 100% | 20 |

50 VU 결과는 실패 요청 시간이 기존 p99 계산에 섞인 실행이므로 p99를 분석에서 제외했다. 이 실행에서 connection reset이 발생했으며, 안전을 위해 100 VU 단계는 수동 중단했다. 중단된 100 VU 수치는 유효한 성능 결과로 사용하지 않는다.

### B 해석

20 VU부터 Hikari active가 최대 연결 수에 도달했고 pending이 발생했다. 30 VU까지는 처리량이 증가했지만, 40 VU에서는 다음 변화가 동시에 나타났다.

- 처리량: 15.83 req/s에서 17.04 req/s로 7.6% 증가에 그쳤다.
- p95: 793.39ms에서 1273.15ms로 60.5% 증가했다.
- Hikari pending: 2에서 10으로 증가했다.
- Hikari active/max: 계속 100%였다.
- Process CPU: 7.60%였다.
- Heap: 56.38%였다.
- Tomcat busy/max: 10.50%였다.
- GC pause: 0.01초였다.

즉 40 VU에서 처리량은 거의 늘지 않는데 응답시간과 커넥션 대기만 증가하는 포화 신호가 확인됐다.

### Hikari 시간 지표 추가 확인

Prometheus에 저장된 각 단계 마지막 1분의 Hikari Timer를 추가로 조회했다.

| VU | connection 획득 평균 | connection 획득 최대 | connection 사용 평균 | connection 사용 최대 |
| ---: | ---: | ---: | ---: | ---: |
| 20 | 42.37ms | 245.89ms | 543.20ms | 620ms |
| 30 | 12.23ms | 152.09ms | 544.50ms | 597ms |
| 40 | 472.18ms | 1006.71ms | 544.00ms | 605ms |

커넥션 사용 시간은 세 단계 모두 평균 약 544ms로 비슷했다. 반면 40 VU에서 커넥션 획득 평균은 약 472ms, 최대는 약 1.01초로 급증했다. 이는 40 VU의 HTTP p95 증가가 커넥션을 획득하기 위한 대기시간 증가와 직접 연결된다는 추가 근거다.

다만 평균 약 544ms의 connection 사용 시간 안에서 SQL 실행, DB 네트워크, JPA 처리 중 어느 부분이 큰지는 아직 분리되지 않았다.

## 현재 결론

이번 실험에서 최초로 확인된 병목 지점은 **DB 접근 이후의 커넥션 점유 구간**이다.

A는 100 VU까지 안정적이었지만 B는 20 VU부터 Hikari 풀이 최대 사용량에 도달했고, 40 VU에서 처리량 정체와 pending 증가가 뚜렷해졌다. 같은 시점의 CPU, Heap, GC, Tomcat thread에는 포화 신호가 없었다.

따라서 현재 결과는 다음 가설과 일치한다.

```text
DB 조회 또는 DB 네트워크 왕복이 커넥션을 오래 점유한다.
-> Hikari의 10개 커넥션이 모두 사용된다.
-> 새 요청이 커넥션 반환을 기다린다.
-> VU를 늘려도 처리량은 거의 늘지 않고 p95와 pending만 증가한다.
```

## 아직 단정할 수 없는 것

`Hikari active 100%`와 `pending 증가`는 관측된 증상이다. 이것만으로 “커넥션 풀이 작으니 개수를 늘리면 된다”고 결론 내릴 수 없다.

근본 원인 후보는 아직 다음처럼 남아 있다.

1. Render와 Railway 사이의 DB 네트워크 왕복 지연
2. 단건 조회 SQL 자체의 실행 지연
3. 커넥션 획득 과정의 지연
4. JPA/Hibernate 처리 비용
5. Railway MySQL 자원 또는 연결 처리 한계

단순히 Hikari max를 늘리면 DB에 더 많은 연결과 부하를 전달해 오히려 상황을 악화시킬 수도 있다.

## 서버 상태와 안전 조치

- 최초 A/B 실행 중 Render 프로세스가 재시작되지 않은 것을 확인했다.
- 테스트 종료 후 `/actuator/health`에서 애플리케이션과 MySQL 연결이 모두 `UP`임을 확인했다.
- 50 VU 실패 후 더 높은 B 부하는 중단했다.
- 최초 C/D 실행은 토큰 불일치로 fixture 준비 단계에서 403이 발생해 실제 부하가 전송되지 않았다.
- 토큰을 바로잡은 뒤 2026-08-23에 C/D 10/20 VU를 완료했으며 결과는 `06-distributed-vs-hot-row-result.md`에 분리해 기록했다.

## 다음 검증

개선 기술을 적용하기 전에 다음 순서로 원인을 더 좁힌다.

1. B의 30/40 VU를 각각 최소 3회 반복해 재현성을 확인한다.
2. Hikari connection acquire·usage 지표를 이후 모든 실행 요약에 함께 저장한다.
3. 강의 단건 조회 SQL의 DB 실행 시간을 측정하고 `EXPLAIN`으로 인덱스 사용을 확인한다.
4. 애플리케이션 내부에서 DB 조회 구간만 Timer로 측정해 HTTP 전체 시간과 비교한다.
5. Render와 Railway의 리전 및 네트워크 왕복 시간을 확인한다.
6. C/D 20 VU 결과를 반복해 동일 강의 row 경합을 재현한다.
7. 조건부 UPDATE 이후 commit까지의 시간을 측정해 lock 보유 구간을 좁힌다.

이 검증이 끝나기 전에는 Hikari pool 증설, 캐시, Redis, 서버 증설을 적용하지 않는다.
