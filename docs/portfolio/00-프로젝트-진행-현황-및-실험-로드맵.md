# 프로젝트 진행 현황 및 실험 로드맵

- 갱신일: 2026-09-01
- 프로젝트: 비공식 단국대 수강신청 연습 서비스
- 운영 환경: Render 애플리케이션 + Railway MySQL 9.4.0
- 목표: 동시성 정합성과 성능 병목을 실제 실험으로 검증하고, 가장 작은 개선을 적용한 뒤 동일 조건으로 재측정한다.

## 현재 한 줄 결론

Race Condition은 조건부 `UPDATE`로 해결했다. Render-Railway C/D 20 VU 반복 실험에서는 동일 강의의 조건부 UPDATE p95가 분산 신청보다 약 10.1배 증가했고 `saveAndFlush()`는 거의 같았다. 따라서 **동일 강의 row의 UPDATE 직렬화가 지배 구간이며 Hikari 대기는 긴 connection 점유의 후속 증상**이라는 근거를 확보했다. 현재는 이 결과를 개선 전 기준선으로 고정하고 최소 개선 하나를 선택하는 단계다.

## 환경을 섞지 않는 원칙

| 실험 | 환경 | 사용 범위 |
| --- | --- | --- |
| 개선 전/후 Race Condition | 로컬 Docker MySQL 8.0 | 정합성 재현과 조건부 UPDATE 검증 |
| 과거 혼합 트래픽 | Render + 메모리 H2 | 포화 현상을 발견한 예비 실험 |
| 현재 A/B/C/D 기준선 | Render + Railway MySQL 9.4.0 | 운영 환경 병목 분석 |

H2, 로컬 MySQL, Railway MySQL 결과는 서로 합쳐 성능 개선 수치로 사용하지 않는다.

## 지금까지 증명한 것

### 1. Race Condition과 정합성

- 정원 10명, 서로 다른 사용자 100명, 동시 요청 100개를 보냈다.
- 개선 전에는 13건이 등록되고 `applied_count`는 12로 남았다.
- 조건부 UPDATE 적용 후 성공 10건, 마감 거절 90건, 정원 초과 0건을 확인했다.
- 실제 신청 행 10건과 `applied_count` 10이 일치했다.
- 동일 사용자의 동시 중복 신청 2건 중 1건만 저장됐다.
- 조건부 UPDATE 뒤 강제 예외를 발생시켰을 때 카운터와 신청 행이 함께 Rollback됐다.

### 2. 최초 포화 경로

- A: DB 없는 ping은 100 VU까지 p95 약 220ms, 78.13 req/s, 실패율 0%였다.
- B: DB 단건 조회는 40 VU에서 p95 1273.15ms, 17.04 req/s였다.
- B 40 VU에서 Hikari active/max 100%, pending 10, connection 획득 평균 472.18ms를 기록했다.
- 같은 시점의 Process CPU는 7.60%, Heap은 56.38%, Tomcat busy/max는 10.50%였다.
- 따라서 이 구간의 최초 포화 신호는 CPU·Heap·Tomcat이 아니라 DB 접근 이후의 커넥션 점유·획득 대기에서 나타났다.

### 3. 분산 쓰기와 동일 row 쓰기

- C는 20개 강의에 신청을 분산하고 D는 하나의 강의에 신청을 집중했다.
- 10 VU에서는 C와 D의 차이가 작았다.
- 20 VU에서 D는 C보다 p95가 약 2.50배 증가하고 처리량이 약 43.5% 감소했다.
- D의 connection 사용 평균은 약 2.49배, 획득 평균은 약 25.2배 증가했다.
- C의 Hikari pending은 0, D는 4였다.
- 두 시나리오 모두 HTTP 실패 0%, `applied_count`와 실제 신청 행 불일치 0건이었다.
- 동일 row UPDATE가 트랜잭션 종료까지 직렬화되며 connection 반환을 늦추는 hot-row 경합으로 분석했다.

### 4. 트랜잭션 단계별 반복 측정

- C와 D를 20 VU로 각각 3회 실행하고 C→D, D→C, C→D로 순서를 교차했다.
- HTTP p95 중앙값은 C 1025.71ms, D 2519.56ms로 D가 약 2.46배 높았다.
- 처리량 중앙값은 C 9.29 req/s, D 5.40 req/s로 D가 약 41.9% 낮았다.
- 전체 트랜잭션 p95 중앙값은 C 709.97ms, D 1771.67ms로 약 2.50배 차이였다.
- 조건부 UPDATE p95 중앙값은 C 140.13ms, D 1413.76ms로 약 10.09배 차이였다.
- `saveAndFlush()` p95 중앙값은 C 107.70ms, D 108.18ms로 거의 같았다.
- D는 세 번 모두 Hikari pending 4였고, 6회 모두 실패·timeout·DB 카운트 불일치는 0건이었다.
- 요청 대상 row 분포만 바꾼 통제 실험 결과가 동일 row lock 대기 해석을 강하게 지지한다. MySQL lock wait 행을 직접 수집한 것은 아니므로 직접 관찰로 과장하지 않는다.

## 11단계 진행 현황

| 단계 | 상태 | 현재 근거 | 다음 작업 |
| --- | --- | --- | --- |
| ① 서비스 구현·운영 | 완료 | Spring Boot, JPA, MySQL, Thymeleaf, Render 배포 | 운영 장애와 사용자 피드백 계속 기록 |
| ② 정원 초과 가능성 발견 | 완료 | `조회 -> 검사 -> 저장` 구조 분석 | 완료 |
| ③ Race Condition 재현 | 완료 | 정원 10명에 13건 등록, 카운터 불일치 | 반복 빈도는 성능 수치가 아닌 재현 근거로만 사용 |
| ④ 동시성 전략 비교 | 완료 | 비관적 락·낙관적 락·조건부 UPDATE 테스트 | 반복 성능 비교가 필요하면 별도 수행 |
| ⑤ 조건부 UPDATE 적용 | 완료 | 실제 신청 경로 적용, 정원·중복·Rollback 검증 | 정합성 유지가 최우선 |
| ⑥ 혼합 트래픽 예비 실험 | 완료 | 500 VU부터 p95 약 9초와 CPU 100% 관찰 | H2 결과이므로 현재 운영 기준선과 분리 |
| ⑦ A/B/C/D 병목 분리 | 완료 | A/B 10~40 VU, C/D 10·20 VU 측정 | 완료 |
| ⑧ 원인 분석 | 완료 | C/D 각 3회, 조건부 UPDATE p95 약 10.1배 차이 | 필요 시 MySQL lock wait 직접 수집 |
| ⑨ 병목 개선 | 준비 중 | 동일 row UPDATE가 지배 구간임을 확인 | 가장 작은 변경 하나를 통제 실험으로 선택 |
| ⑩ 동일 조건 재테스트 | 미시작 | 개선안 미적용 | 개선 전과 같은 C/D 20 VU로 비교 |
| ⑪ 장애 대응 문서화 | 일부 완료 | Micrometer, Prometheus, Grafana 구성 | 알람·탐지·조치·복구 타임라인 작성 |

## 바로 다음 실험

### Priority 1. 최소 개선 후보 검증

- 동일 row 쓰기는 정합성을 위해 직렬화된다는 제약을 먼저 인정한다.
- 측정 결과가 거의 같았던 `saveAndFlush()`를 근거 없이 병목으로 단정하지 않는다.
- 가장 작은 변경 하나만 적용하고 C/D 20 VU를 각각 3회 재측정한다.
- 개선이 없으면 결과를 숨기지 않고 가설을 기각한다.

### Priority 2. MySQL lock wait 직접 수집

- C/D 실행 중 Railway MySQL `performance_schema` 사용 가능 여부 확인
- `data_lock_waits`와 `data_locks`를 수집해 동일 row 대기 직접 검증
- Timer 기반 추론과 DB 내부 관찰 결과 비교

### Priority 3. B 조회 경로의 약 544ms 분리

- B 30/40 VU 최소 3회 반복
- 단건 조회 SQL 실행시간 측정
- `EXPLAIN`으로 PK 인덱스와 실행 계획 확인
- HTTP 전체 시간과 애플리케이션 DB 조회 Timer 비교
- Render와 Railway 리전 및 네트워크 왕복 지연 확인

### Priority 4. 개선 후 동일 조건 재측정

측정 결과에 따라 하나만 선택한다.

| 확인 결과 | 첫 개선 후보 |
| --- | --- |
| 조건부 UPDATE 이전 검증 조회가 큼 | 불필요한 사전 조회 또는 SQL 수 축소 검토 |
| `saveAndFlush()`가 큼 | flush 위치와 INSERT/index 비용 검토 |
| UPDATE 이후 commit 구간이 큼 | 트랜잭션 범위와 lock 보유 구간 축소 검토 |
| 단건 조회 SQL은 빠르고 전체 DB 시간이 김 | Render-Railway 네트워크와 JPA 구간 검토 |
| 원인을 줄인 뒤에도 풀 대기가 남음 | Hikari pool 크기를 통제 변수로 재검토 |

개선 전·후에는 Render 플랜, DB, 데이터, Hikari 설정, VU, Ramp, Hold, 워밍업을 동일하게 유지한다.

## 아직 단정하면 안 되는 표현

- `500명을 안정적으로 처리했다`: VU는 실제 동시 사용자 수가 아니며 500 VU의 p95는 약 9초였다.
- `Render CPU가 병목이었다`: 최신 Render-Railway A/B/C/D 실험에서는 CPU가 낮은 상태에서 DB 대기가 먼저 나타났다.
- `Hikari pool 크기 10이 근본 원인이다`: active와 pending은 느린 DB 작업 또는 lock 대기의 결과일 수 있다.
- `조건부 UPDATE가 항상 가장 빠르다`: 현재 강하게 검증한 것은 정합성이다.
- `성능 병목을 해결했다`: 현재는 병목을 좁히고 직접 시간을 측정하는 단계다.
