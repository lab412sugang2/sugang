# 프로젝트 진행 현황 및 실험 로드맵

- 작성일: 2026-08-20
- 프로젝트: 비공식 단국대 수강신청 연습 서비스
- 운영 URL: `https://sugang-5de3.onrender.com`
- 목표: 실제 사용자가 이용하는 연습 서비스에서 동시성 정합성과 성능 병목을 측정하고, 개선 후 동일 조건으로 검증한다.

## 현재 결론

현재는 **동시성 전략 비교와 혼합 트래픽 예비 측정까지 완료했고, 병목의 근본 원인을 분리하는 실험 직전**이다.

지금 증명한 것은 다음과 같다.

- 수강신청 처리는 `@Transactional`로 묶여 있다.
- 비관적 락, 낙관적 락, 조건부 `UPDATE`를 같은 조건에서 실행하는 MySQL 동시성 테스트가 있다.
- 100개 동시 요청, 정원 10명의 비교 실험에서 세 전략 모두 최종 등록자를 10명으로 유지했다.
- 해당 1회 실험에서 조건부 `UPDATE`가 전체 소요시간과 성공 요청 p95 기준으로 가장 짧았다.
- Render 배포본에 혼합 트래픽을 보냈을 때 500 VU 구간부터 p95가 크게 증가했고 CPU 100%가 관찰됐다.

아직 증명하지 못한 것은 다음과 같다.

- 동시성 제어가 없는 기준 방식에서 정원 초과가 실제로 발생하는지
- 조건부 `UPDATE`가 반복 실험에서도 가장 유리한지
- CPU를 100%로 만든 주요 처리 경로가 Render 자원, 화면 렌더링, DB 조회, 쓰기 트랜잭션, 락 경합 중 무엇인지
- 개선 전·후 성능 차이

## 동시성 전략 비교 결과

실험 조건:

- MySQL
- 서로 다른 학번 100개
- 동시 요청 100개
- 스레드 풀 32개
- 강의 정원 10명

| 전략 | 성공 | 마감 거절 | 락 충돌 | 기타 실패 | 전체 소요시간 | 성공 요청 p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 비관적 락 | 10 | 90 | 0 | 0 | 154ms | 91ms |
| 낙관적 락 | 10 | 27 | 63 | 0 | 113ms | 101ms |
| 조건부 `UPDATE` | 10 | 90 | 0 | 0 | 100ms | 32ms |

세 방식 모두 다음 정합성 검증을 통과했다.

- `courses.applied_count <= courses.limit_count`
- 성공 건수 = 실제 `course_applications` 행 수
- `courses.applied_count` = 실제 `course_applications` 행 수

해석:

- 비관적 락은 성공·마감 결과가 명확하지만 동일 row 접근을 직렬화한다.
- 낙관적 락은 경합이 큰 상황에서 63건의 충돌이 발생했다. 재시도 정책이 없으면 사용자 실패로 노출된다.
- 조건부 `UPDATE`는 `WHERE applied_count < limit_count`를 DB가 하나의 원자적 SQL로 판단하며, 해당 실험에서 충돌 예외 없이 10건만 성공시켰다.

제한:

- 현재 결과는 1회 실험이므로 성능 우위를 최종 확정하기에 부족하다.
- 현재 테스트는 **성공한 요청의 지연시간만** p95 계산에 포함한다. 충돌·마감 요청을 포함한 전체 요청 p95를 별도로 측정해야 한다.
- 낙관적 락 실험 중 MySQL deadlock 로그가 관찰됐다. 예외 분류와 재시도 정책을 별도로 검증해야 한다.

## 혼합 트래픽 예비 결과

| VUs | p95 | p99 | 실패율 | req/s | 관찰 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 100 | 약 238~242ms | 약 286~321ms | 0% | 약 77 | 안정적 |
| 300 | 약 390ms | 약 598ms | 0% | 약 223 | 안정적 |
| 500 | 약 9.01s | 약 11.6s | 0% | 약 88 | p95 급등, CPU 100% |
| 1000 | 약 9.45s | 약 15.29s | 약 0.04~0.05% | 약 119 | timeout 일부, CPU 100% |

이 결과로 말할 수 있는 범위:

> 혼합 트래픽에서 500 VU 구간부터 응답시간이 크게 증가했고, 같은 시점에 CPU 100%가 관찰됐다.

아직 말하면 안 되는 범위:

> DB 병목은 없었다. Render CPU가 근본 원인이었다. 500명을 안정적으로 처리했다.

이유:

- VU는 현실의 동시 접속자 수와 완전히 같은 개념이 아니다.
- Hikari 지표가 0으로 기록된 것은 병목이 없었다는 증거가 아니다. 메트릭 노출·Prometheus 라벨·쿼리를 먼저 검증해야 한다.
- 혼합 트래픽은 여러 처리 경로가 섞여 있어 CPU 사용의 직접 원인을 분리하지 못한다.

## 다음 실험 순서

### 1. 제어 없는 Race Condition 재현

배포 코드가 아닌 테스트 전용 전략으로 `조회 -> 정원 확인 -> 저장`을 동시 실행한다.

검증할 것:

- 정원 10명을 초과하는 실제 행 수
- `courses.applied_count`와 실제 신청 행 수의 불일치
- 예외가 없어도 데이터가 틀릴 수 있다는 점

### 2. Rollback 검증

조건부 `UPDATE`로 정원을 증가시킨 뒤 신청 내역 저장 직전에 의도적으로 예외를 발생시킨다.

검증할 것:

- `courses.applied_count`가 기존 값으로 돌아왔는지
- `course_applications`에 행이 추가되지 않았는지

### 3. 동시성 전략 재측정

- 각 전략을 최소 3회 반복한다.
- 성공·마감·충돌 요청을 모두 포함해 p95/p99를 계산한다.
- 데드락, 락 충돌, 재시도 횟수를 분리한다.
- 정합성을 먼저 통과한 전략만 성능 비교 대상으로 삼는다.

### 4. A/B/C/D 병목 분리

| 테스트 | 요청 | 분리하는 비용 |
| --- | --- | --- |
| A | `GET /performance/ping` | DB 없는 Render·JVM·Tomcat 기본 처리 |
| B | `GET /performance/courses/{id}` | DB 연결·조회·네트워크 |
| C | 여러 강의에 분산 신청 | 일반 쓰기·트랜잭션 |
| D | 하나의 강의에 집중 신청 | hot row·락 경합 |

현재 A/B/C/D 엔드포인트, k6 시나리오, 자동 집계 스크립트는 구현되어 있다. 실제 Render 배포본에서 의미 있는 결과 표를 만드는 실행 단계가 남았다.

### 5. 근본 원인 확정

A/B/C/D 결과와 다음 지표를 같은 시간축으로 비교한다.

- CPU·Heap·GC
- Tomcat busy/max thread

- 요청당 SQL 수와 쿼리 지연시간
- 트랜잭션 수행시간
- MySQL lock wait·deadlock

## 포트폴리오 서술 초안

### 제목

> 동시성 제어와 성능 병목 분석 중심의 수강신청 백엔드 시스템

### 한 줄 소개

> 실제 사용자가 이용하는 비공식 수강신청 연습 서비스를 운영하며, 동시 신청의 데이터 정합성과 고부하 상황의 성능 병목을 직접 재현·측정하고 기술적 의사결정을 검증한 프로젝트입니다.

### 현재 사용 가능한 서술

> 정원 10명의 강의에 100개의 동시 요청을 발생시켜 비관적 락, 낙관적 락, 조건부 UPDATE의 정합성과 응답 특성을 비교했습니다. 세 방식 모두 정원 초과를 방지했으며, 1차 실험에서 조건부 UPDATE가 락 충돌 없이 가장 짧은 소요시간을 보였습니다. 다만 반복 실험과 전체 요청 지연시간 측정 후 최종 선택을 확정할 예정입니다.

> Render 배포본에 100·300·500·1000 VU의 혼합 트래픽을 발생시켰습니다. 500 VU 구간부터 p95가 약 9초로 증가하고 CPU가 100%에 도달한 현상을 관찰했습니다. 현재는 DB 미사용, DB 조회, 분산 쓰기, 동일 row 집중 쓰기로 경로를 분리해 CPU 포화의 근본 원인을 검증하고 있습니다.

## 포트폴리오에서 아직 쓰지 말아야 할 표현

- `500명을 안정적으로 처리했다`: VU와 실제 동시 사용자는 다르고, 500 VU에서 p95가 약 9초였다.
- `DB는 병목이 아니었다`: Hikari 0 수치의 신뢰성을 먼저 검증해야 한다.
- `CPU 병목을 해결했다`: CPU 100%를 관찰했을 뿐, 직접 원인과 개선 효과는 아직 미검증이다.
- `조건부 UPDATE가 항상 가장 빠르다`: 현재 조건의 1회 실험에서 가장 좋았을 뿐이다.
- `Race Condition을 재현했다`: 제어 없는 기준 전략의 정원 초과 수치를 아직 보관하지 않았다.
